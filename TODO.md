## Note on the autoscaling item's scope

"GCP Cloud Run like" autoscaling as literally described (spin up *N* replicas of a service, load-balance across them, scale back down) needs a real rearchitecture this codebase doesn't have today: `service.containerId` is a single column, `createAndStartContainer`/`findServiceContainer`/status reconciliation/the Overview tab's start-stop-restart actions all assume exactly one container per service. Building real elastic replicas means that whole chain becomes 1:many first — a bigger, separate change from "add a scheduler." What got built instead uses the *existing* one-container-per-service model plus the *existing* Remote Hosts primitive: when the local host is over threshold, one opted-in service gets *moved* (not replicated) onto a designated overflow host. That's a genuine, working "never exceed 80% of the main host" safety valve — just load-shedding, not horizontal scaling. If you want real multi-replica load-balancing later, that's the "Homerun Agents" control-plane rearchitecture from the original note, and it deserves its own design pass rather than retrofitting it onto today's data model.
