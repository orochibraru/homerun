# Subproject Sync

You maintain the three standalone sub-projects that live alongside `src/` in
this repo but are NOT part of the SvelteKit build: `agent/`, `installer/`,
`cli/`. Each has its own `package.json`... actually no — they share the root
`package.json`/`bun install`, but each has its **own `tsconfig.json`** and is
typechecked separately (`check:agent`/`check:installer`/`check:cli` root
scripts, or `bunx tsc --noEmit -p <dir>/tsconfig.json` directly). None of them
are covered by `bun run check` (that's `svelte-kit sync && svelte-check`,
SvelteKit-only).

## `agent/` — the Homerun Agent

A token-authenticated HTTP server meant to run on a remote host's Docker daemon.
It has **no access to the main app's source tree at runtime**, so
`agent/src/docker.ts` and `agent/src/stats.ts` are deliberate, from-scratch
reimplementations (not imports) of the equivalent logic in
`src/lib/services/docker/containers.ts` and
`src/lib/services/system-stats.service.ts`.

**If you change deploy/container-lifecycle logic in
`src/lib/services/docker/containers.ts`**
(pull→remove-previous-by-label→create→start shape, container naming, label
conventions, etc.), check whether `agent/src/docker.ts` needs the equivalent
change to stay behaviorally consistent, and make it by hand — there is no shared
module, no codegen, no automated sync. Same for `system-stats.service.ts` ↔
`agent/src/stats.ts`.

**If you change the agent's request/response shapes**, update
`agent/src/schemas.ts` (the zod schema backing `/v1/deploy`'s validation) and
`agent/src/openapi.ts` (generates the agent's own OpenAPI doc from that same
schema) together — same "one schema, two purposes" pattern as the main app.

## `cli/` — the Homerun CLI

Built on `openapi-fetch` against the main app's REST API (`src/routes/api/v1/`).
`cli/src/generated/openapi-types.ts` is generated by `openapi-typescript` from a
**running instance's real** `/api/v1/openapi.json` — it is checked in as a
snapshot and goes stale silently (no compile-time staleness detection) if the
REST API's shape changes without regenerating.

**If you change any route under `src/routes/api/v1/`** (new endpoint, changed
request/response shape, changed `$lib/openapi/registry.ts`/`schemas.ts`),
regenerate: boot the app (`bun run dev` or against a running instance), then
`bun run generate` inside `cli/` (check `cli/package.json` for the exact script
name). Flag to the user explicitly if you can't actually run this (e.g. no live
instance available) rather than leaving the snapshot silently stale — this is a
documented sharp edge in this repo, not a hypothetical.

## `installer/`

Single-binary installer targeting a fresh Linux server (rootless Docker setup,
systemd units, `--mode=agent`/`--mode=full`). Every shell-out goes through one
`StepRunner` (`installer/exec.ts`) so `--dry-run` stays a single interception
point — don't add a step that shells out directly, route it through the runner.
Real mutating steps (package install, `useradd`, actual rootless Docker
bring-up) are **not safely testable in this environment** — verify via
`--dry-run` output only, and say so plainly rather than claiming something was
verified live when it wasn't.

## Always finish with

- The touched sub-project's own typecheck:
  `bunx tsc --noEmit -p <dir>/tsconfig.json` (or the root `check:*` script).
- Its own test suite if relevant: `bun test:agent` / `bun test:cli` /
  `bun test:installer`.
- `bun run lint` (biome covers the whole repo including these directories).

None of these are covered by `bun run check` alone — don't report a sub-project
change as verified based on that command by itself.
